# dsh 升级 SOP

> 立此文档的起因：2026-09-28 升级 dsh 0.1.5-rc.2 → 0.1.7-rc.2，升级后生产 bot
> 会话无法创建（`presets.standingKeyFor is not a function`），且升级当时无任何验证环节。

## 一、版本口径（2026-09-28 定）

**rc 可以跟，但每次升级必须跑契约验证 + 测试，且要有版本记录。**

- 不拒绝 rc：软件不能抱着老版本不动
- 但 rc 意味着 API 可能变，必须用验证兜住
- 稳定版与 rc 版**都走同一套验证流程**（rc 的风险靠验证消化，不靠"不升"规避）

## 二、标准流程（五步 + 发布前文档门，缺一不可）

升级 dsh 前，在 `dsh-lark-bridge` 目录依次执行：

```bash
# 步骤 1｜升级前先跑门禁，拿到基线
npm run contract-drift      # 对照上游 master 检查契约签名

# 步骤 2｜切换 dsh 版本
#   修改 web 端的启动脚本 里的两个路径指向新版本（apps/cli/lib/bin.js + node_modules）

# 步骤 3｜类型检查（最便宜的 API 变更探测器）
npm run typecheck           # 桥接镜像的 host.ts 若对不上，这里会报

# 步骤 4｜全量测试
npm test                    # 全量（条数随版本变化，以实测为准）；覆盖会话创建、命令、后台任务通知等

# 步骤 5｜重建 + 重启 + 真实验证
npm run build
systemctl restart <桥接服务>
#   ★ 必须真的发一条飞书消息给生产 bot，确认会话能建、能回复
```

**步骤 6｜文档与 README（打 tag 之前）**：见第九节。代码对了、门禁全绿，但对外文案还停在上一版，
等于发了一份错的说明书——这一节就是防这个。**它不是收尾事项，是发版流程里的一步。**

## 三、验证的三道闸门

| 闸门 | 命令 | 抓什么 |
|---|---|---|
| 契约漂移 | `npm run contract-drift` | 上游签名增删改（按已知清单 + 镜像项反向校验） |
| 类型检查 | `npm run typecheck` | 桥接 `src/host.ts` 镜像与真实 API 不匹配 |
| 行为测试 | `npm test` | 会话创建、斜杠命令、任务通知等真实路径 |

**外加人工闸门**：发一条真实消息。**服务 `systemctl is-active` 返回 active 不代表能用**——
2026-09-28 事故中服务是 active 的，但一创建会话就抛异常。

## 四、事故复盘：为什么这次没兜住

三处 0.1.7 不兼容，**门禁一处都没抓到**：

| 变更 | 性质 | 为什么门禁漏了 |
|---|---|---|
| `presets.standingKeyFor` → `acquireScope` | API 改名 + 返回值变化（返回可释放租约） | agent-preset 包**不在门禁校验名单里** |
| `jobs.onJobDone` → `jobs.events.subscribe` | **API 整体移除**，改事件订阅 | jobs 校验项写的是旧签名 |
| `jobs.list` 参数/返回类型变化 | `Agent`→`SessionId`、`JobSnapshot`→`JobView` | 同上 |

**根本教训**：门禁只校验"**已知清单**"里的签名。**上游增删整个 API 面时，静态清单抓不到。**

对策 = 新增 `scripts/audit-host-contract.mjs`（**反向排查**）：
把桥接 `src/host.ts` 里镜像的每一个方法**逐个拿去 0.1.7 里找**，找不到就报。
清单式的查"上游有没有 A"，反向的查"我依赖的每一个还在不在"。两者互补。

```bash
node scripts/audit-host-contract.mjs   # 需 DSH_HOME 或默认定位 0.1.7 目录
```

**没有台账的升级等于没有升级记录**——下次出问题无从比对。

## 六、沉淀纪律

- 每次升级踩到的坑，**当场**写进 `docs/开发经验.md`（不是事后回忆）
- 新增的契约校验项，**当场**加进 `scripts/verify-dsh-contract.mjs`

## 七、已知遗留

- `tests/midturn-followup.spec.ts` 全量跑时偶发超时（3 次跑 1 次失败；单独跑必过）。
  与本次升级无关，属测试稳定性问题，待独立处理。
- `HostSettings.register` 在 0.1.7 中已无对应实现（旧 `SettingsProvider` 服务被拆成
  `SettingsForms` + `dsh-api-settings-controller`；`SettingsProvider` 类型已从上游消失）。
  **实测结论（2026-09-28）：无影响。** `src/runtime.ts:347` 读 `ctx.get('settings')`，
  本部署该服务为 `undefined`，整段（含 `register` 调用）被跳过——启动日志无
  `settings registration failed`。该段代码本身即按"服务可能不存在"设计，并有 try/catch 兜底。
  **故不改，仅登记。** 若未来部署提供了 `settings` 服务，此处会降级（丢配置持久化）而非崩溃。
- 仓库 CRLF 问题：`git diff` 显示 32 文件全改（实为行尾符差异），需统一换行符配置，
  否则后续所有代码审阅都无法辨别真实改动。

## 八、v2 增补（2026-10-18）

起因：0.2.x 两次升级（10-10）未入台账、桥侧兼容验证无记录；9/30 的一处改动在工作区悬挂 18 天。
以下四条与上文五步并用：

1. **以 `dsh-upgrade.sh` 为主轴**（`部署侧脚本 dsh-upgrade.sh`：check / prepare / switch / rollback / status）。
   切树、冒烟、回滚由脚本承担；五步中的「改路径 → 重启」由 `switch` 代劳，桥侧门禁照跑。
2. **台账更新 = switch 后的硬步骤**：切完当场在 `docs/dsh版本台账.md` 追加一行（日期/版本/变更/验证）。
   没有台账的升级等于没有升级记录。
3. **桥侧兼容验证在每次引擎升级后强制重跑**：`npm run contract-drift` + `npm run typecheck` + `npm test`，
   结果写进台账；随后实发一条飞书消息确认端到端。缺一不可。
4. **工作区整洁纪律**：当天产生的改动要么当场提交、要么明确丢弃，禁止让未提交改动过夜
   （9/30 悬挂事故的教训）。部署配置（persona、restartCommand 等）的修改同样留一行记录。
5. **重启前先查活动（2026-10-19 增补）**：`systemctl restart` 会掐断正在跑的 turn——用户的任务会停在半路、最终汇报永远发不出来。
   重启（含为部署而重启）前必须查：会话文件 mtime（`ls -l ~/.dsh/sessions/.../session.v*.jsonl.zstd`）、`journalctl` 近几分钟有无活动。
   活跃则等它跑完或先问用户；这比"马上部署"重要。

## 九、文档与 README（发布即更新）

**这一节是第 6 步：在步骤 5 之后、打 tag 之前。**

理由三条，按分量排：

1. **测试数与台账结论是步骤 4/5 跑完才存在的事实。** 先写文档就是先编数字——本仓这么错过一次（见 9.5）。
2. **tag 一推，README 就固化了。** `package.json` 的 `files` 里含两份 README，npm 页面与 GitHub Release
   展示的就是 tag 里那一份。tag 之后再补，改的是下一版；**已发布的版本永远带着错的说明书**。
3. **步骤 5 的「真发一条消息」是唯一能证明功能表为真的动作。** 功能表照刚验过的行为写，不照设计意图写。

只发桥、不换引擎的版本，步骤 2/3 不适用，**本节整节照跑**：它是发版闸门，不是升级的附属品。

### 9.1 什么改动必须改 README（判据）

**一句话判据：只要用户能观察到行为变化，就有一处对外文案要改。找不到是哪一处，说明这个改动对外是什么还没想清楚。**

| 改动性质 | 必改位置（`README.en.md` 与 `README.md` **两侧**） |
|---|---|
| 新增 / 改名 / 删除一条斜杠命令 | 斜杠命令表、`/bot` 子命令行、`docs/用户手册.md` 第三节、`src/user-guide.ts` |
| 新增 / 删除一个 `/bot` 子命令 | 命令表下的子命令行 + 手册 |
| 新增 / 改名配置项，或改默认值 | 配置表（字段 / 默认 / 含义三列都要对；默认值以 `src/config.ts` 的 schema 为准） |
| 媒体、工具、能力的语义变化 | 功能表对应行（亮点表 + 「全部能力」表）。语义变了而描述没变 = 对外撒谎 |
| 测试数变化 | 徽章 `tests-N passing`、仓库地图 `vitest suites (N)`、质量门注释 `# N ...`（两侧共 6 处） |
| 宿主契约检查项数变化 | 仓库地图 + 质量门注释（共 4 处 `43`） |
| 宿主版本下限变化 | 两侧「Harness 版本」行 + **写清为什么是硬下限**（哪一处 API 在哪一版才有 / 没了）+ EN 的 `Moving to a new harness version` |
| Node / pnpm 要求变化 | 两侧 Prerequisites，且与 `package.json` 的 `engines` 一致 |
| `src/` 下增删文件或目录 | 两侧仓库地图 |
| 扩展点、钩子或其载荷变化 | 两侧 Extend It + 配置表对应项（载荷字段要逐个点名） |
| 飞书应用权限变化 | 两侧权限表——手动建应用的人只能照它授权 |
| 发布流程、门禁命令变化 | 两侧「开发与 MR 流程」+ 本文档 |
| **目录收录状态变化**（新目录收录 / 版本显示变了 / 链接失效） | 两侧「生态与收录」表——**每条链接发版前实访一遍**，写不写版本号见 9.7 |
| **治理文件新增或改名**（CONTRIBUTING / SECURITY / CODE_OF_CONDUCT / Issue 模板） | 两侧「参与」段——**文件存在但 README 没指过去，等于文件不存在** |

### 9.2 必查清单（逐项打勾，缺一项不算发版）

| # | 查什么 | 合格判据 |
|---|---|---|
| 1 | 版本三处一致 | `package.json` 的 `version`、`CHANGELOG.md` 顶部最新段、待打的 tag，三个字符串相同 |
| 2 | 计数两口径都对 | **测试数**（徽章 ×2、质量门注释 ×2）等于步骤 4 实测；**套件数**（仓库地图 ×2）等于 `tests/*.spec.ts` 的文件数。两者不是一回事，混用过一次（仓库地图里写了测试数）⇒ `node scripts/sync-test-count.mjs` 一次改齐 6 处 |
| 3 | 命令表两侧 | 命令集合完全相同；`/bot` 子命令也逐个写下来了。**门会验这一项**（命令表 ⊇ 代码里的命令、且每条都是真命令） |
| 4 | 功能表两侧 | 亮点行数相同；每条能力在两侧都有对应描述；**新增能力必须在两侧同时出现** |
| 5 | 配置表两侧 | 字段集合相同；每个默认值与 `src/config.ts` 一致（语义项要人读） |
| 6 | 仓库地图两侧 | `src/` 条目集合相同，条目说明与当前职责相符 |
| 7 | 扩展说明两侧 | 两侧都存在对等小节（现状见 9.4 第四行） |
| 8 | 版本台账 | `docs/dsh版本台账.md` 追加一行，四字段必填（日期 / 版本 / 变更要点 / 验证结果），验证写命令与结论 |
| 9 | 手册 ↔ `/manual` 源 | `docs/用户手册.md` 与 `src/user-guide.ts` 归一化后逐行一致。**门会验这一项**（chat 版是运行时真给用户的那份，以它为准） |
| 10 | CHANGELOG | 有对应版本段；条目按「首现于哪个 tag」归属，不按主观分类 |
| 11 | 泄漏门 | `node scripts/check-repo-hygiene.mjs . --lib --patterns-file .leak-patterns` 退出 0 |
| 12 | 收录链接可达 | 两侧「生态与收录」表里**每一条**都用 HTTP 实访取到 200；取不到的条目改 URL 或删掉，**不留在表里当摆设** |
| 13 | 治理文件被指到 | 两侧「参与」段列出的每个文件在仓根真实存在（`CONTRIBUTING.md` / `SECURITY.md` / `CODE_OF_CONDUCT.md` / `.github/ISSUE_TEMPLATE`） |

第 8 项的格式见第五节；这里只强调它是**本节清单的一项**，不是升级之余的随笔。

### 9.3 怎么验（可直接复制）

```bash
# ① 测试数（权威口径）：跑一遍，读末行 "Tests  N passed"
node node_modules/vitest/vitest.mjs run --reporter=dot   # 平时用 npm test，等价
#   2026-10-21 实测：57 文件 / 563 例 / 645 秒（单 fork 串行，慢是正常的）

# ② 测试数（静态口径，用来交叉核对；与①应是同一个数）
grep -ohE '(^|[^.[:alnum:]_])(it|test)(\.(each|skip|only|todo|concurrent))?\(' tests/*.ts | wc -l
#   ★ 别写成 grep "it("：会漏掉与 describe 同行的 it(，又会把 /re/.test( 数进来。
#     2026-10-21 实测：错写法 562，对写法 563（差的那条在 feishu-tools.spec.ts 的 describe 同一行）。
#   套件数是另一回事（仓库地图里写的是它）：ls tests/*.spec.ts | wc -l

# ③ 契约检查项数（应与 README 的 43 一致）
node plugin-contract-test.mjs | tail -1

# ④ 改完代码后先把计数同步到位（一条命令，6 处数字）
#   —— 不在 CI 里跑：CI 要的就是「忘了改就红」，本地才自动改。
node scripts/sync-test-count.mjs

# ⑤ 仓库自带的文档门（CI 已在跑）：命令表两侧 + 与 src/commands.ts 对账 + 徽章
#   + 套件数 + 章节数 + /bot 子命令 + 手册与 /manual 源逐行
node scripts/check-docs-consistency.mjs

# ⑥ 泄漏门
node scripts/check-repo-hygiene.mjs . --lib --patterns-file .leak-patterns
```

**门管不到、要人读的两处**：配置表的字段集合与默认值（对着 `src/config.ts` 的 schema 看）、
功能表每条描述是否仍与真实行为相符（对着刚才实测过的行为看，不对着设计意图看）。

**门管不到的一处**：配置表的字段集合与默认值（要跟 `src/config.ts` 的 schema 对）、
`/bot` 的**子命令在正文里**（门已覆盖，但正文的**语义**是否仍然对，要人读）。
这两处靠人读，门给不了。

**不要养第二套门。** 门抓到的东西若反复出现，就并进 `scripts/check-docs-consistency.mjs`；
并进去时连测试一起写（`tests/docs-consistency.spec.ts`），否则下一个改门的人会把它改坏。

### 9.4 这张单子第一次跑抓到了什么（2026-10-21）

四类，同一天抓到的：

| # | 位置 | 抓到的东西 | 性质 |
|---|---|---|---|
| 1 | `README.md` 仓库地图 | `tests/ vitest 套件（0 个）`，而徽章与源码静态计数都是 `563`（当时的数；现在门会直接比套件文件数） | 数字错 |
| 2 | `docs/用户手册.md` 第 13 行 | 把 `/balance` 并进「钱袋与说明」一行；源里 `/balance` 只在「钱袋」一节，「反馈」是单独一行 | 同一句话的两种结构 |
| 3 | `docs/用户手册.md` 第 16、33 行 | 「批量重活会优先」对「批量重活**我**会优先」；「bot 和你」对「我和你」 | 同一句话的两种写法 |
| 4 | EN / ZH 结构 | EN 有 `### Moving to a new harness version`（切树、profile 只声明自己的依赖两条规则），ZH 无对应小节 | 一侧有、一侧没有 |

**第 1 类最值得记：徽章是对的，套件栏是错的**——同一个仓库地图里两个数字，一真一假。
**四类都不会让任何测试变红。** 修法是把这四类都变成门里的判据（徽章、套件数、章节数、`/bot` 子命令），
所以现在跑门就会红；下面 9.4 记的是「门长出来之前」抓到的东西。

另一个盲区在测试本身：`tests/user-guide.spec.ts` 第四条只断言手册包含 8 个小节标题和 4 个命令，
**不比对正文**。实测 33 行里 3 行不同，它照样绿。仓库的文档门按「行集合」比（不按顺序），
能抓到增删、抓不到错位与顺序。

修没修、修到哪，看提交与台账。**本节只记「清单抓到了什么」——判据是从这些样本里长出来的。**

### 9.5 为什么不能省：两次实证都在本仓

**一、2026-10-20 的批次**：对外文案四处与真实行为不符——「无需登录」（实际裸开地址 401）、
`chronicle` 写成 `full-transcript`（实际只发入站用户文本）、宿主版本下限写 `>=0.1.5-rc.2`
（代码硬依赖 0.1.7 才有的 `acquireScope`，在旧宿主上组建会话直接抛错）、测试数与契约项数的**名词**写错
（`43` 是「契约检查项数」，不是断言数）。**四条都不影响构建，所以门禁一处都没抓到**；
逐条见 `docs/功能缺口清单_20261020.md` 第 23 条。

**二、同一类错的第二个样本**：`ca82e4a` 把 `README.md` 的测试数写成 `0`，同一批把英文的 `562`
改成 `563`。两侧朝相反方向改，没有任何门拦——**因为徽章一直绿着，没人会回头数一个自己刚写下的数字**。

两次的共同点：**错的不是代码，是发布出去的那份说明书**。用户拿到的第一条信息是 README，不是测试报告；
文档错的代价不是重启一次，是他照文档操作失败之后不再相信这个仓库。

### 9.6 收录表：不写会过时的数字（2026-10-21 实证）

今天的第二批把「生态与收录」从 3 条扩到 9 条 ⇒ **这不是新增功能，是补一句实话**：
仓库早已被 9 个目录收录，而 README 只写了 3 个——**那 3 个恰好是手工提交过的，
自己填的就记得，别人收录的就没写**。同一类错误还有第二处：仓里有 `CONTRIBUTING.md`、
`SECURITY.md`、`CODE_OF_CONDUCT.md` 和 Issue 模板，README 一个都没指 ⇒ **文件存在
不等于读者找得到**。

**两条纪律，从今天这两处错里长出来：**

1. **收录表不写版本号。** 九个目录里有一半的版本是从 npm 读的，而 npm 上仍是 `0.6.1`
   ⇒ 一旦写进去，下次 npm 发版它就是假的。写「已收录」+ 写清**收录方式**（提 issue /

### 9.7 与沉淀纪律的接口

- 新增命令 / 配置项时，**改 README 与改代码在同一个提交里**。发版前只该剩「核对」，不该还有「补写」。
