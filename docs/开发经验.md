# dsh-lark-bridge 开发经验（2026-08-20 沉淀）

> 整理自 P008 完美插件开发过程中踩过的坑与验证过的方法。
> 适用范围：本仓库开发、Windows + pnpm + vitest 环境、dsh 生态插件开发。

## 一、环境与工具链（Windows）

### 1. node_modules junction 损坏
- **症状**：tsc 报 `Cannot find type definition file for 'node'`、vitest/pnpm 卡死、pnpm install 报 `EACCES lstat qrcode-terminal`。
- **根因**：pnpm 重建 node_modules 中途被中断，`.pnpm` 下的真实包还在，但顶层 junction（typescript / vitest / tsdown / qrcode-terminal / @types/node）全部变成坏链接。
- **修复**：`cmd /c rmdir <坏junction>` 后重新 `New-Item -ItemType Junction` 指回 `.pnpm/<pkg>/node_modules/<pkg>`。
- **预防**：pnpm install 必须跑到结束；中途杀掉进程会留下坏链接。修完先 `cmd /c dir @types\node` 验证。

### 2. 单次 shell 调用有 ~12s 超时
- 长命令（pnpm install、完整 vitest）会超时被杀，**不要前台硬跑**。
- 正确姿势：`Start-Process cmd /c "..." -WindowStyle Hidden -PassThru`，输出重定向到 log，然后分批轮询 `Get-Process -Id` + `Get-Content log -Tail`（每次 sleep ≤8s，避免再次超时）。

### 3. Node 版本
- 仓库要求 `node ^22.19 || >=24`，本机 22.16 只产生 warning，不影响安装/测试。

### 4. vitest 4 的 reporter
- `--reporter=basic` 不存在（会被当成自定义模块加载失败），用默认或 `--reporter=default`。

### 5. 不要用 `npx tsc`
- 会把 `tsc@2.0.4` 错误包装进来。用仓库内真实编译器：
  `node node_modules/.pnpm/typescript@6.0.3/node_modules/typescript/bin/tsc -p tsconfig.json --pretty false`

## 二、PowerShell 写 Python 脚本的转义

- **双引号 here-string（@"..."@）里反引号是 PowerShell 转义符**，写 backtick 必须双写，写 Python 字符串里的转义极容易变成 `\a`（BEL 字符）或错误转义。
- **推荐：Python 脚本一律用单引号 here-string（@'...'@）**，内容是字面量，再在 Python 里用 raw string（前缀 r），backtick/反斜杠都安全。
- Python 字符串里 `\a` 是 BEL（0x07），不是“反斜杠+a”，写文件路径/注释要小心。
- 文本替换脚本要验证每个 replace 是否命中（`if old not in t: raise`），避免“看似成功实则没改”。

## 三、dsh 契约对齐方法论

### 1. 先读上游源码，再写窄拷贝
- 桥不 import 上游包，靠 `src/host.ts` 结构拷贝；**载荷形状必须以 deepseek-harness 源码为准，不能猜**。
- 实测教训：第一版把 `agent/status` 载荷猜成 `{agentId, status}`，实际是 `{agent: Agent, status}`；`skills/change` 无载荷；`workflow/log|phase` 是双参数 Cordis 事件 `(info, text)`，不是 session event。
- **dsh 默认分支是 `master`，不是 `main`**（raw 拉取地址要用 master）。

### 2. 事件分两类，作用域不同
- **durable session events**（`session/event` 载荷）：`todo/write`、`goal/change`、`tool-workflow/*`、`compaction/*`、`schedule/change`、`subagent/descriptor` —— 通过 `ctx.on('session/event', ...)` + type guard 消费。
- **live Cordis events**：`agent/*`、`subagent/start|end`（`Scoped<Agent>/Scoped<SubagentRuntime>`，注册在 agentCtx 才收到）、`workflow/*`（全局，双参数）、`skills/change`（无载荷）。
- 新事件类型通过 `declare module '@deepseek-ai/cordis'` 增强 Events，桥才 typecheck 通过。

### 3. 契约漂移门禁
- `scripts/verify-dsh-contract.mjs`：fetch `raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/...` 关键文件，正则校验 host.ts 镜像的关键签名，漂移即 exit 1。
- GitHub Actions（`.github/workflows/ci.yml`）：contract-test → typecheck → drift → vitest。

### 4. inject 保持最小
- `inject: ['agents', 'goals']` 是硬依赖；可选服务一律 `ctx.get(...)` 降级（settings/loader/commands/sessionPersistence/agentPresets/workspaceRegistry/sessionQuery/jobs）。

## 四、dsh 架构关键认知

- Everything is a plugin + Cordis；profile/bundle/patch 分层叠加，无特权内核。
- ~62 个 capability seams、22 个 tool package；桥只消费与 IM 交互相关的子集。
- **“全部官方功能在飞书可用”不是好目标**：编辑器/LSP/PTY/代码调试/设置页属于官方 Web UI。飞书桥应做“适合 IM 的官方功能深度原生呈现 + 通知/审批/断点续跑”，不适合的给一句话入口。
- 飞书桥差异化三张牌：全生命周期可视、断点续跑（autoResumeGoals）、决策留痕（审批卡 + /audit）。
- 战略边界（用户 2026-08-20 定调）：不追求官方 org scope/官方列表认证；做好自己的插件；生态融入量力而行、尊重他人意向。

## 五、测试方法论

- **Windows 路径**：不要用 `lastIndexOf('/')` 切路径，用 `node:path` 的 `dirname/join`。
- **harness 模式**（tests/harness.ts）：
  - fake agents 的 `compose` 用**独立的 `new Context()`**，测试服务要在 agentCtx 上 `provide`（例：jobs 必须 `createFakeAgents({ jobs })` 传进 agentCtx，只 provide 到根 ctx 拿不到）。
  - 集成断言用 `vi.waitFor(() => expect(harness.fake.sent.some(...)).toBe(true))`。
  - 测实时事件：先发 durable 建立映射（如 `tool-workflow/run-start` 建立 runId→chat），再 emit 对应 live 事件。
- **质量门禁**：改完先跑 tsc（直接二进制）→ plugin-contract-test.mjs → 全量 vitest；全绿才提交。当前基线：258 tests / 41 contract checks / drift green。

## 2026-10-18 深夜增补：复核对红抓到的两个硬伤（都要记）

- **「目标 spec 绿」不等于「套件绿」**：本批提交前只跑了相关 3 个 spec（87/87）就放行，分支全量其实是 8 failed——
  被独立复核当场对红。规则：任何提交/推送前跑全量 `vitest run`；只测局部=没测。
- **测试必须隔离落盘目录**：轮换存储读 `DSH_HOME`（测试未设 → 写进了真实 `~/.dsh`，与线上服务共用该文件），
  跑一次测试就污染运行态、还会连锁弄红下一次别的 spec。规则：凡测试路径里会落盘的 store，harness 必须先
  指向临时 home（`DSH_HOME=mkdtemp()`），并做一次「跑完无外部写入」的复查。
- 两条同源教训：①静默 catch 只要没人看返回码，就是价值黑洞——`record()` 改为返回 boolean，由 UI 层把失败说出来；
  ②并发路径要有 in-flight 守卫（同一会话的 /new 串行化 + 到达消息等轮换落定），否则「快按两下」就能把状态撕成两份。

## 2026-10-20 增补：升级 0.2.1-alpha.2 → 0.2.1-rc.2 的三处坑

- **「树起不来」可能是探针自己掐死了它**：升级脚本的试启动用 `timeout 150` 起进程、轮询 200s。rc.2 冷启动到
  能应答 HTTP 实测要 ~160s（/mnt/d 是 drvfs，读盘慢），于是进程在就绪前被 `timeout` 杀掉，升级被判"起不来"并
  中止——连着两轮都这样，而生产树纹丝未动。规则：**升级探针的 timeout 必须大于实测冷启动时间的 2 倍以上**；
  判"起不来"之前先手工跑一次同一棵树排除探针问题。已把 timeout 提到 600s、窗口提到 900s。
- **`pnpm build` 不等于产物齐全**：`build:lib:client` 的 tsc 阶段在**测试文件**上报错（exit 2）时，后面的
  tsdown bundle 根本不会跑，于是 `packages/client/*/lib` 只有 tsc 产出的 `types/`，缺 `index.js`/`client.js`；
  运行时表现为 web 起不来、日志里一片 `Cannot find module .../dsh-client-ui-*/lib/index.js`。
  而 dsh-upgrade.sh 的体检（`lib 目录数 ≥ 包数`）只看**目录是否存在**，不查里面有没有 js——293/347 时
  目录都在，体检骗过去了。规则：**体检要查 lib 里的产物文件，不只查目录**；tsc 失败但目录已建时不能当作构建成功。
- **冒烟判据会随上游漂移而误报**：`code-runtime-worker-thread` 上游在 0.1.7-rc.2 起就已移除
  （0.1.5-rc.2 时还在）、`dsh-mcp-client` 并不是上游默认存在的（rc.2 全仓只有技能模板提到它，
  本部署有它是因为 chat/web profile 自己 insert 了）——旧判据一正一反全错，会把"上游改了"报成
  "部署回归"。规则：**判据漂移要分清是"上游改了"还是"我们坏了"**：拿上一版树跑同一判据做对照，
  别直接改判据了事；**也别把"我们配了"当成"上游默认"**。
- **npm 发版通道是断的**：仓库的 `release.yml` 只建 GitHub Release，**没有 npm publish 步骤**；本机无 npm
  登录态、Actions secrets 里也没有 NPM_TOKEN。后果：0.7.0 之后的版本**一个都没进过 npm**（npm 上 latest 仍
  是 9-03 发布的 0.6.1），所以 issue 报障人装到的还是老包、遇到的是早已修好的 bug。
  规则：**「代码里修了」≠「用户拿到的版本修了」**；没有 publish 步骤的发布流程，等于没有发版通道。

- **「client 面包完了」≠「host 面包完了」**：rc.2 的 host 面独有 `typert.host.js` /
  `typert.remote-client.js`（由 tsdown 的 `dsh-typert-generator` 插件产出），client 面构建
  **不产出**它们。只跑 `build:lib:client` 的结果是：dsh-commands 等 30 个包的 lib 里没有
  typert.host.js ⇒ 启动时 typert-loader 逐个 import 失败 ⇒ **25 个贡献者注册失败**，
  日志里 51 行错误。规则：**dsh 有 host/client 两面，部署前两面都要构建**；
  `tsconfig.host.json` 是 noEmit 的类型检查单元（17 分钟、内存紧时 OOM），产物在
  `tsdown --env.DSH_BUILD_FACE host`。
- **「目录存在」≠「产物齐全」**：升级脚本的体检只数 lib 目录数，rc.2 缺 typert.host.js 时
  目录照样在 ⇒ 体检全绿 ⇒ 切过去才炸。规则：**体检要查具体产物文件**（`lib/index.js`、
  `lib/typert.host.js`），并且**构建不许 `|| true` 吞错**——构建失败必须让 prepare 失败。
  三处假绿（探针 timeout、目录计数、吞错）叠在一起，就是一轮"体检全过但生产报错"。

- **契约测试断言「桥自己的声明」= 自指，只能防自己改主意，看不见上游漂移**。
  本轮真 bug（tokenMeter 恒为 0）就是被自指断言**认证为正确**的：断言写的是
  `measure(session: { readonly id: string })`，而上游要的是 `measure(session: Session)`。
  阴性对照最狠：把声明改得**更正确**（加 `seq`），契约测试反而变红——门在保护错形状。
  规则：**形状类断言要分两层**——①桥内形状快照（自己读自己的代码，防自己漂）；
  ②上游签名比对（读上游 master 源码，findings 才算数）。缺 ② 层 = 上游改了形状你不知道。
- **上游签名是 `Session` 这类对象时，传 id 是「静默失败」不是报错**：上游 `_sync` 读
  `session.seq`（传 id 时 undefined），`while (consumedEvents < undefined)` 恒 false ⇒
  一次都不重放 ⇒ 返回全 0，**且不抛错**。这类 bug 没有任何日志线索，只能靠
  「同一服务两处调用形状不一致」发现（本轮正是：`/context` 传 `agent.session` 对、
  轮询传 `{id}` 错）。规则：**同一服务出现两处调用时，比对它们的参数形状**。
- **`lib/index.js` 指向单个 hash bundle 时，只跑 `tsc` 不会改变生产行为**。
  改了 src 必须 `tsdown` 重出 bundle 并重启，否则生产仍在跑旧码——而「typecheck 过、
  测试全绿」会给人已上线的错觉。

## 2026-11-05 增补：定时任务面板——三个「读返回值」的坑

做 `/schedules` 的读写面板时，宿主 `@deepseek-ai/dsh-schedule` 的三处接口形状和直觉不一致，
每一处都会让「看起来成功了」变成静默失败：

- **`update` 的 `expected` 是整条记录的全量比对，不是 id**。服务内部
  `isDeepStrictEqual(current, decodeScheduleRecord(expected))`，所以必须先 `list()` 拿到
  当前 record 原样回传；少一个字段就是 `schedule_conflict`。规则：**比较并交换（CAS）类接口
  要回传「你刚读到的那份」，不要自己拼一个「等价」的对象**。
- **拒绝是 `{code}` 返回值，不是异常**：`delete` 答 `{deleted:false, code:'schedule_not_found'}`，
  `update` 答 `{updated:false, code:'schedule_conflict'|'schedule_ended'|'subagent_session'}`，
  `history` 答 `{id, code:'delivery_cursor_not_found'}`。全都 resolve 不 reject ⇒
  **只写 `try/catch` 会把「没删掉」报成「已删除」**。规则：**变更类调用必须读返回值的
  `updated`/`deleted` 字段，并把 `code` 翻成人话**。
- **`list()` 只回 `task.record`，不带 `lastDelivery`**（`catalog()` 才带，但它跨会话）。
  「上次什么时候跑的」要另发一次 `history({limit:1})`；历史页是 `{records, nextBefore,
  earlierRecordsUnavailable}`，`records.length` 是**本页条数**，不是累计投递次数——
  当成总数显示会把跑了几个月的任务少报成 10 次。

另外记一条事件侧的：`schedule/change` 的 `dispatch` 事件只保证有 `id`，任务名和规则要从
桥自己登记的 registry 里补——桥旧实现正因为「dispatch 静默」让定时投递看起来像人在说话。

## 2026-11-05 增补：`/think off` 关不掉思考——off 档该「发参数」还是「不发言」

用户报「设了 `/think off`，下一次还是思考」。桥本身没坏（会话日志里 `model/selection` 记了
`reasoningEffort:"off"`，之后每个 `request/header` 都带 `off`），坏在**off 档翻译成什么 wire 值**。

**pi-ai 的 off 语义是二选一，由 `reasoningEfforts` 的写法决定**（`dsh-llm-pi-ai`
`resolveModelReasoning` → `thinkingLevelMap`）：

| YAML 写法 | `thinkingLevelMap.off` | 实际发给上游 |
|---|---|---|
| `"off": none` | `'none'`（字符串） | `reasoning_effort: "none"` |
| `"off": null` | 键不存在 | **什么都不发** |
| 删掉 `off` 这一行 | `null`（= 不支持） | `/think` 里**选不到 off** |

所以想「真关」，必须写 `"off": null`——写 `none` 是「发一个叫 none 的档位」，不是关闭。
删掉那一行更糟：`getSupportedThinkingLevels` 会把 off 判成不支持。

**上游不认 `none`**：直接对 magpie 网关（`auto/deepseek-v4.1-flash`）做对照实验，
同一 prompt、只看 `usage.completion_tokens_details.reasoning_tokens`：

| 传的 `reasoning_effort` | 实际思考 token |
|---|---|
| `none` | 52 / 65 |
| `low` | 105 / 93 |
| `high` | 60 / 60 |
| `max` | 50 / 400 |
| **字段不传** | **0 / 0** |

即「只要收到 `reasoning_effort` 就会思考，`none` 只被当成一个 effort 名字」。
上线后复核 `~/.config/magpie/routing/<date>.jsonl`：修复前 648 条请求 `effort:"none"`、
思考 token 平均 200.1。

> **注意**：这张表和上面「上游不认 none」的结论都是当时用 `reasoning_effort` 直连测的，
> 成立。但当时没意识到的是——**那个 `"none"` 根本不是 DSH 发的**，而是 magpie 自己记的。
> 见下面修正后的根治一节，那里才是完整链路。

### 谁在把 `null` 改回 `none`：是 magpie，不是 DSH

当时写下「写回者不存在」「只读是误判」，**这两句后来都被证伪了**，改写如下。

真正的写回者是 **magpie**（`D:\Tools\Magpie\magpie.exe`，托盘常驻）。它把 DSH 当作被接管的
agent 之一（`magpie dsh` 会直接打印它管的文件：`~\.dsh\profiles\web\cordis.patch.yml`），
周期性把每个模型的 `reasoningEfforts` 块整块重新渲染进
`~/.dsh/settings.yaml` 和全部 5 个 profile patch。

- **一次写全 6 个文件、间隔 40–80ms**，这是 magpie 的标志性特征，也是当初误判成
  「DSH 遍历 profile 写回」的原因。
- **它认的是内容差异，不是定时器**：`magpie dsh effort <档位>` 一次就把 4 个 profile patch
  在 43ms 内重写（实测 13:27:39.993–13:27:40.036）。反过来，文件不动它就一行都不写。
- **手改成 `null` 或整行删掉，都会被写回 `none`**。用 `magpie model efforts <模型> off`
  （它自己的语义就是「send it no reasoning field at all」）也不行——实测写出来仍然是
  `"off": none`。这是 magpie 的渲染行为，改配置绕不过去。
- **只读属性确实能挡住它**，这一点当初也判错了：`IsReadOnly=True` 期间 `null` 能稳定
  保持 40 分钟以上，一解锁就变回 `none`。之所以当初觉得「挡不住」，是因为观察窗口里
  混着别的写入（见下一节的会话混用）。不过加锁只是权宜——被锁住的文件会让整个
  profile 无法正常编辑，不能当长期方案。

### 根治（第一版走错了，这里是修正后的）

**先说走错的那一版。** 当时的想法是「既然配置里的 `reasoningEfforts.off` 随时被打回 `none`，
那就不依赖它，在 `agent/request` 拦截器里把 `off` 换成『字段缺席』」：

```ts
if (wanted === EFFORT_OFF) {
  const { reasoningEffort: _dropped, ...rest } = resolved
  return rest            // 键整个不在信封里
}
```

**这一版是错的，而且错得很隐蔽**：它让 `options.reasoningEffort` 变成 `undefined`，
而宿主第 1953 行是 `resolveReasoningLevel(model, options.reasoningEffort ?? profile.reasoning)`
——**`??` 回落生效**，于是所有档位（low/max 也一样）都走了回落路径，全都静默。
用户的反馈是「现在好像没思考了，但是我设置 `/think low` 或者 `max` 也没有思考了」。

这就是「一次修复制造新 bug」的典型：只验证了 `off` 这一个档位，没回归其他档位。

**真正的根因在两端语义不一致，不在桥：**

| 环节 | 它理解的「关闭」 |
|---|---|
| magpie（写配置的一方） | 字符串 `"none"` |
| `dsh-llm-pi-ai`（读配置的一方） | `null`（键不存在） |

`resolveModelReasoning` 只把 `null` 当「这一档没有 wire 值」，字符串一律原样塞进
`thinkingLevelMap`。于是 `"off": none` 被理解成「off 档的 wire 值是字符串 none」，
请求发出去带 `reasoning_effort: "none"`；magpie 网关自己也不认这个值，
按 `fitEffort` 跳过 `none` 收敛成 `low`（路由日志里 `none -> low` 出现 1178 次）。

**修复落点因此不在桥，在适配器。** `D:\CodexWork\dsh-patches\patch-reasoning-none.mjs`
给 `dsh-llm-pi-ai` 打一行补丁：

```js
- else if (wire !== null) map[level] = wire;
+ else if (wire !== null && wire !== "none") map[level] = wire;
```

效果：`"off": none` 不再往 `thinkingLevelMap` 写 `off`，与 `"off": null` 完全等价，
pi-ai 不再往请求里放 reasoning 字段；而 `low/high/max` 照常映射，档位选择不受影响。

补丁脚本是幂等的，改的是已安装的构建产物（这个包没有可构建源码），
**DSH 升级或重装会覆盖，升级后重跑一次即可**；脚本会先备份 `.orig` 再做语法校验，改坏自动回滚。

### 这个 bug 上游认不认

- **magpie 认了，但还没修完**：[issue #1098](https://github.com/yetone/magpie/issues/1098)
  「reasoning off 被静默收敛成 low」，作者 yetone 亲自定位到
  `internal/catalog/catalog.go` 的 `mdModel.efforts()` 只读 `{"type":"effort"}`、
  跳过 `{"type":"toggle"}`，所以带 toggle 的模型没有 `none` 档，`fitEffort` 就把关闭请求收敛成 `low`。
  2026-10-07 确认、10-13 说「还没发」，到 10-29 仍有人实测复现，issue 至今 open。
  有人提了 fork 补丁（`Niko-Wu/magpie` 的 `fix/oss-batch`）实测有效，但仓库不收 PR。
- **DSH 那边没人管**：`deepseek-ai/deepseek-harness` 关掉了 issue 功能（`has_issues: false`），
  只有 discussion。讨论区里有 [#122 第三方模型无法选择推理强度](https://github.com/deepseek-ai/deepseek-harness/discussions/122)
  解释 `reasoningEfforts` 的声明方式，但**没有人报过「`none` 应该当 `null`」这个语义问题**。
  社区插件 [dsh-thinking-effort](https://github.com/hytime/dsh-thinking-effort) 做的是自动补档位
  和自定义 wire 值，也没有覆盖这个点。

结论：短期只能自己绕，绕法是上面的补丁。magpie 修好之后这个补丁可以撤。

### 三个部署坑（排错顺序也按这个来）

- **配置只在进程启动时读一次**。改完不重启等于没改；反过来，**只要启动那一刻文件是对的，
  之后写回方再覆盖也不影响已经载入内存的进程**。所以正确顺序是「停 → 改 → 起」。
- **`wscript.exe` 里裸写 `pwsh.exe` 会静默失败**——wscript 的 PATH 不含 PowerShell 7，
  脚本一次都不执行，但 `Start-Process` 照样返回成功。规则：**投递后台任务必须留落地探针**
  （脚本第一行写一行 `boot <时间>` 到日志），否则「已启动」全是猜的；可执行文件一律写绝对路径。
- **`~/.dsh/settings.yaml` 是 legacy 文件，不是 profile patch 的 `- id:` 序列**，它是
  `llm-pi-ai:` 顶层段落。`dsh-settings` 启动时若发现它存在，会先 rename 成
  `settings.yaml.imported` 再逐段 `update()` 导入——所以「`.imported` 里的写法」就是
  原始意图的存档，比对它和现文件的差异，比翻会话日志靠谱得多。

### 排查方法论：一次观测只能证明一件事

这一天里前后得出了七八个互相矛盾的结论（宿主写回 / 没人写回 / 只读没用 / `none` 是
YAML 序列化产物 / PID 2180 是写回者），每个都是「一个数据集被多个假设共用」导致的。
可复用的规矩：

- **改 1 个文件，看其余 5 个动没动**——能立刻区分「单文件修复」和「全局重渲染」。
- **先测「什么都不做」的基线**：静置 45–60 秒记录 mtime，0 次写入，才说明是内容触发。
- **Procmon 别猜二进制偏移**。PML 里字符串条目格式是 `u32(0x8000|长度)` + 字节；
  但 PID 在 512MB 抓包里一次都没出现，说明事件按进程索引、不存裸 PID。在拿到
  可信校准（用已知 PID 的 canary 写入反推偏移，并验证覆盖率）之前，任何「某偏移
  是 opcode/PID」的结论都不成立。

排查这类「改了不生效」的问题，顺序建议是：先确认**请求有没有带上设定**（会话事件的
`request/header`）→ 再确认**wire 值对不对**（网关自己的请求日志）→ 再看**配置与部署**。
本次三层都在，桥的代码确实无辜；但**配置这一层被别人接管**才是真根因。
