# 设计卡：文件/图片发送失败要在聊天里说得出来

> 状态：现行设计 · 2026-10-30 建档 · CHENJIAMIAN

## 1. 目的与非目标

**目的**：`send_file` 发不出去时，聊天里出现一条明确的失败提示，而不是一段「关于文件名的文字」让人以为文件已经发出。

**起因**（2026-10-30 真机反馈）：用户说「你发图片过来，我好像只能收到文本，就是关于图片名称之类的文本」。

查宿主日志，实证是：

```
dsh-lark-bridge: replay flush failed: local file source requires
  `outbound.allowedFileDirs` to be configured
```

即部署白名单没配、传输层拒绝上传。而 `deliverFile` 当时的顺序是**先发 caption（说明文字）再发媒体**——图片被拒之后，caption 已经在聊天里，于是用户看到的正是「一句关于文件的话，没有文件」，失败原因只落在工具结果和宿主日志里。

**非目标**：

- 不改 `SendInput` 的联合语义（caption 仍然必须是独立消息）。
- 不改媒体 kind 的判定规则（扩展名 / 显式 kind / 容器能力）。
- 不自动重试（拒绝是配置问题，重试无意义）。

## 2. 架构与数据流

改动前：

```
caption（markdown 消息） → 媒体上传/发送 → 返回 { fileName }
                                 ↑ 失败就 throw，caption 已留在聊天里
```

改动后：

```
媒体上传/发送 ─ 成功 → caption（markdown 消息）→ 返回 { fileName }
            └ 失败 → sendFailureNotice 进聊天 → throw（工具结果带原因）
```

要点：

- **顺序**：媒体在前、说明在后。失败时聊天里没有任何「看起来像成功」的残留；成功时图片在上、说明在下，也更符合阅读顺序。
- **失败提示**：`sendFailureNotice(fileName, detail)` 生成一条 markdown，包含文件名与传输层原文；若原文含 `allowedFileDirs`，追加一句可操作的配置提示。
- **caption 失败不翻案**：媒体已经送达，说明文字发不出去只静默丢弃——文件才是要的东西，不能因为一句话把整次投递判成失败。

## 3. 契约设计

- 新增导出 `sendFailureNotice(fileName, detail): string`（可单测）。
- `deliverFile` 的媒体发送包在 `try/catch` 里；`catch` 中先发提示（`catch(() => undefined)`，提示失败不能再掀翻原始错误），再抛出带上下文的错误。
- 返回类型 `DeliveredFile` 不变。

## 4. 失败路径

| 失败 | 处理 |
|---|---|
| 路径不在 `outbound.allowedFileDirs` | 提示里点名该配置项；工具结果为失败，模型可据此转述 |
| 上传超限 / 网络错误 | 提示带传输层原文，不再吞掉 |
| 失败提示本身发不出去（连接断） | 静默；原始错误仍抛出，日志仍有记录 |
| caption 发送失败 | 静默丢弃，投递仍算成功 |
| 白名单正确、媒体成功 | 行为与之前一致（多一条 caption 顺序变化） |

## 5. 测试三层

- **mock 单测**：`tests/files.spec.ts` 新增「传输层拒绝时聊天收到失败提示、caption 不出现、调用仍 reject」；`files.spec.ts` 与 `tests/media-outbound.spec.ts` 中 caption 顺序断言改为「文件/媒体在前」。
- **plugin-contract**：未新增（不改宿主接口）。
- **smoke-live**：2026-10-30 真机确认图片能正常到达（白名单配置好后）；失败路径由单测覆盖。
