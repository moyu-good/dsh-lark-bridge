# 设计卡：设备迁移与多机（/bot export + /bot import）

> 状态：🚧 开发中 · 2026-09-03 立（zcode）· 需求方提出「设备发生变化或者迁移了怎么办」
> 前置：《设计卡_双端设置与同步》（P091）——本卡覆盖其第 5 节预判的「跨机退化」场景

## 1. 背景

P091 的三层同步绑定**同一台机器**的 `~/.dsh`：settings 单源、peers 心跳、会话共享全部依赖同机文件系统。换设备/迁移/多机场景未覆盖：

1. **旧机退役 → 新机接管**：飞书凭证、插件清单、桥设置要过去；peers.json/token/node_modules 是活体垃圾不能带走。
2. **多机并存**：settings 单源跨机失效；同一飞书 appId 两机同连 = 事件双投递双回复（P091 已知坑）。
3. **重装/换机**：`dsh plugin add` 逐个重装太原始，凭证要靠 onboarding 重扫。

## 2. 目标

1. `/bot export`：旧机一键导出「可迁物」为单文件。
2. `/bot import`：新机读文件 → 设置就位 + 插件清单可一键装回。
3. 迁移安全三件套：活体零残留、凭证默认掩码、跨主机导入必提醒防双投递。

## 3. 设计

### 3.1 导出物（`bridge-migrate-<ts>.json`）

```json
{
  "kind": "dsh-lark-bridge-migration",
  "version": 1,
  "exportedAt": "<iso>",
  "from": { "profile": "web", "form": "web", "host": "<hostname>" },
  "settings": { "…SharedSettings…": "…" },
  "profiles": { "web": { "dependencies": {…}, "bundles": […] } },
  "notes": { "hint": "sessions live in ~/.dsh (upstream-owned), copy the directory to carry them" }
}
```

### 3.2 凭证策略（两档）

- `/bot export`（默认）：secret 字段经 `maskSecret` 掩码 → 文件可安全存放；导入端需 `/bot set appSecret <新值>` 补录。
- `/bot export include-secrets`：明文包含，回复中显式警告「此文件含凭证，勿经不可信渠道传输」。

### 3.3 活体排除（导出物天然干净）

导出物是构造性 JSON，不含 peers.json（旧机心跳）、control token（每启动轮换）、锁文件、node_modules/pnpm store（跨机二进制不兼容，重装才是对的）、`~/.dsh/sessions`（上游职责，notes 指路拷目录）。

### 3.4 导入流程（`/bot import [file]`）

1. 文件定位：无参 = 读 `<syncDir>/migrate.json`；带参 = sync 目录内相对文件名（拒绝路径穿越）。
2. 校验：kind/version 不符或 JSON 烂 → 明确报错，**不写任何东西**。
3. settings：合并写入本机 settings.json（复用 updateSettings 的备份机制）。
4. profiles：与本地清单 diff → 输出待装计划 → 人工确认后走 `applySyncPlan`（复用 P091 M4 已验证管线：dry-run→确认→装，enable 步骤强制人工确认）。
5. 双投递防护：`from.host` ≠ 本机 hostname 时，回复**必含**提醒「旧机桥若仍在运行请先停，否则同 appId 双连消息双回复」。
6. 输出迁移报告（装了什么、需补录什么、提示哪些）。

### 3.5 多机并存（非迁移场景）

- peers 心跳天然支持 N 端互见（`/bot peers` 全量可见）。
- settings 跨机共享：维持既有决策——`DSH_SYNC_HOME` 指同步盘（用户自选），或各机独立需要时 export/import。
- 同 appId 多机同连：**禁止**，一台活跃其余 standby，或每机独立飞书自建应用。

### 3.6 边界（不做）

- 不做网络同步服务；不迁会话历史（上游 `~/.dsh` 职责）；不自动停旧机（无法触达，只给指引）。

## 4. 交付切分

- **M1** `src/sync/migrate.ts`：`buildExport()`（收集 settings+清单，掩码开关）、`applyImport()`（校验+写设置+返回装包计划）、迁移文件类型与校验。
- **M2** bot-command 接线：`export` / `export include-secrets` / `import [file]` 子命令，装包沿用 sync-plugins 确认流。
- **M3** i18n 词条 + 测试（fs mock：往返、掩码、坏文件零写入、确认流、双投递提醒）。
- **M4** README 双语 + 设计卡回填。

## 5. 验收

1. 导出 → 清空 → 导入：settings 就位、插件清单一键装回、活体零残留。
2. 默认导出 secret 掩码；`include-secrets` 显式开启且带警告。
3. 坏文件零写入。
4. 跨主机导入必现双投递提醒。
5. 门禁：tsc + vitest 全绿 + leak 干净。

## 8. 后续规划（待需求方拍板）

### M2 · 迁移文件走飞书云盘（消除跨机拷贝）
- `/bot export --to-feishu`：导出文件直传自建应用的云空间（drive 权限）；
  新机 `/bot import --from-feishu` 直接拉取——零拷贝、天然 app 隔离边界。
- 前置：需求方在飞书开放平台给自建应用加**云文档/云空间读写** scope。
- 安全：凭证明文档建议用 appSecret 派生密钥加密后上云。

### M3 · 多机常驻 + 云端仲裁（真「转来转去」）
- 目标形态：N 台机器桥常驻、都连飞书长连接，但只有「活跃设备」应答——
  活跃者记录存飞书云文档（天然单源+版本历史），每台收到消息先查仲裁
  （本地缓存 60s），非活跃者静默丢弃。
- `/bot activate` 语义升级：写云端仲裁 → 其它机器在下一个消息窗口自动退避，
  无需人工逐台 retire。
- 前置：同 M2 的云文档权限 + API 限频评估（按消息查而非心跳查，频率可控）。
- 风险：飞书 API 不可达时的 fallback（本地最后已知仲裁 + 兜底活跃，宁可
  双回复不可全哑）。
