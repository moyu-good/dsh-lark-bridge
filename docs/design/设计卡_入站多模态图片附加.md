# 设计卡：入站多模态图片附加（inbound multimodal image attach）（dsh-lark-bridge）

> 状态：现行设计 · 2026-08-29 建档 · hermes

## 1. 目的与非目标

**目的**：让飞书里的图片能安全地进入模型请求——只有「当前模型确实是视觉模型」时才附加图片，纯文本模型照旧收到一条 note 而不是一个会被 API 拒绝的请求。配套原则：**多模态模型走硅基流动 Qwen3-VL（30B 主力 / 8B 兜底）**，用于测试与开发。

**非目标**：
- 不做图片解析/OCR——那是模型与上游能力，桥只做「传不传」的判定。
- 不做按消息/按会话的模型路由（那是 dsh host 与 /model 的职责）。
- 不改变出站图片（send_file / 出站图片管道另卡，阻塞于上游 image 事件源）。

**背景**：桥既有 `attachImages` 布尔开关，默认 false（config.ts 注释写明：纯文本模型的 API 会拒绝整条带图请求）。8/28 升级评估（docs/dsh_upgrade_plan_20260829.md 项 F「attachImages 默认开启」）发现：无脑开启会让 deepseek-v4-flash 等纯文本模型收到图就整条 400/拒绝。要开，必须先有「模型感知」层。

## 2. 架构与数据流

```
飞书消息(resources: image)
      │
      ▼
bridge.ts (channel 收到消息)
      │  config.attachImages == true?
      │  且 config.visionModelPrefixes 非空?
      │    ├─ 非空 → 取 modelSelection().model（config.model 或 host 默认）
      │    │        prefixes.some(prefix => modelId.startsWith(prefix))
      │    │        ├─ 命中 → imagesEnabled = true
      │    │        └─ 未命中 → imagesEnabled = false, note = '当前模型不接受图片…'
      │    └─ 空（部署只有一条已知视觉路由）→ imagesEnabled = true（保持原布尔语义）
      ▼
images.collectImages(msg, port, attachments, enabled, reason)
      │  enabled == true → 下载、按 store 上限裁剪、saveImage、附加 image block
      │  enabled == false → 只生成 note（'用户发送了 N 张图片…：<reason>'）
      ▼
agent turn（模型只看到它吃得下的东西）
```

## 3. 契约设计

| 字段 | 类型 | 默认 | 语义 |
|---|---|---|---|
| `attachImages` | boolean | `false` | 总开关（原字段，语义不变） |
| `visionModelPrefixes` | string[] | `[]` | 视觉模型 id 前缀白名单。`[]`=保持 attachImages 纯开关；非空时按当前模型 id `startsWith` 命中才附加 |

实现点：
- `Config` 接口（可选入参）+ `ResolvedConfig`（必填）+ zod schema（`z.array(z.string()).default([])`）+ `resolveConfig` 透传
- `images.collectImages` 增加第 5 参 `reason = 'attachImages 未开启'`——note 文案区分「通道没开」与「当前模型不吃图」
- `bridge.ts` 调用处：用 `modelSelection().model` 判白名单（config.model/provider 优先，回落 host default）

## 4. 失败路径

| 路径 | 防线 | 事故背书 |
|---|---|---|
| 纯文本模型（deepseek-v4-flash）收到图 → 整条请求被 API 拒 | visionModelPrefixes 白名单拦截 → note 而非附加 | config.ts 注释：图片已进会话日志，拒绝后每轮重发，会话直接死（2026-08-22 多模态失效根因链） |
| 漏配白名单却开了 attachImages | 空数组=纯开关语义保留——部署自担风险（文档:只适合单一已知视觉路由） | 未遇事故，属文档化取舍 |
| 模型 id 取不到（host 无默认） | `?? ''` 空串不命中任何前缀 → note 安全侧 | modelSelection 抛错路径已有原逻辑兜底（no model configured） |
| 30B 视觉节点异常/排队 | 8B 兜底模型已在 catalog；/model 可切 | 8/29 实测 30B 60s 无响应、8B 0.8s 秒回 |

## 5. 测试三层

- **mock 单测**（plugin.spec.ts image input describe）：
  - 白名单配置 + 非视觉默认模型 → content 仅 note，`attachments.saved` 空
  - 白名单配置 + model=Qwen/Qwen3-VL-30B-A3B-Instruct → image block 附加
  - 既有用例回归（attachImages=false → note；attachImages=true 无白名单 → 附加）
- **plugin-contract 43 项**：config 新增字段不影响 host 契约面，跑通即可
- **smoke-live 真链路**：部署重启后 9 项断言（config 组合树含硅基流动 + 面板模型菜单新增两项）
