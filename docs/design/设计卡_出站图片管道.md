# 设计卡：出站图片管道（agent 产出图 → 飞书图片消息）

> 状态：🚧 调查完毕 · 阻塞于上游证据 · 2026-08-23 建档（ths）
> 结论先行：传输层零障碍；宿主侧未见图片事件源——按「嫁接桥」铁则不抢先造能力，上游落地后本桥为小补丁。

## 1. 目的与非目标

**目的**：agent 运行产出的图片（run_code 图表、terminal 截图等）以飞书原生图片消息送达聊天，补齐「PC 有的聊天全有」的最后一块富媒体。

**非目标**：
- 不做图片生成能力本身（那是宿主/模型层的事）
- 不做图片编辑、相册管理

## 2. 可行性调查记录（2026-08-23 实测）

| 层 | 状态 | 证据 |
|---|---|---|
| 飞书通道发送 | ✅ 原生支持 | `@larksuite/channel` `SendInput` 判别联合已含 `{ image: { source: string \| Buffer } }`（dist/index.d.mts:160-167），上传封装通道自带 |
| 桥侧渲染管线 | ✅ 接入点明确 | `OutboundRenderer` 在 turn 收尾处已有逐 item 分发；新增 image 分支即可 |
| 宿主事件源 | ❌ 未证实 | `HostSessionEvent` 全谱系（assistant/message、tool/result、tool/call、step/start、turn/end）内容块实测只见 `type:'text'`；harness CLI bundle 无 `'image'` 字面量；pi-ai 协议中图片历来是 USER 输入侧块。未发现任何 `output_image` 类事件 |

## 3. 上游解锁条件（满足其一即可开工）

1. dsh 上游在 `tool/result` 或 `assistant/message` 内容块中暴露 `type:'image'`（附 path/base64/fileKey 任一载体）
2. 或官方确认 PC 端同样不渲染生成图 → 本设计卡归档为「无需求」

## 4. 届时实现预案（小补丁）

```
turn 收尾遍历 content blocks
  └─ type==='image'
       ├─ source=path → readFileSync / 直接路径（channel 支持 string|Buffer）
       ├─ 安全门：复用 outbound.allowedFileDirs 白名单（防工具伪造路径读敏感文件）
       └─ send(to, { image: { source } }, { reply 目标同 turn 正文 })
```
七处清单对照：commands.ts 无新命令（事件驱动非 slash）；i18n/panel 不涉及；host.ts 若需新增 `HostImageOutput` 最小契约走可选字段模式；tests/harness.ts 注入 fake image 事件；contract-drift 复跑。
