# 设计卡：问询卡片重做（dsh-lark-bridge）

> 状态：现行设计 · 2026-11-07 建档 · 运营方提问触发

## 1. 目的与非目标

**起因是三个连续的提问，不是一次需求评审：**

> 当前 ask_user_question 工具只支持选择吗？支持用户输入吗

> 飞书支持哪些表单组件

> 一个打磨得非常好的产品，这个询问用户问题的表达组件应该长什么样

查证结论：宿主侧 `@deepseek-ai/dsh-tool-ask-user` 的协议本来就支持自由文本 ——
`options` 是可选参数，答案结构里的 `custom` 字段注释为
*"Optional free-text 'Other' answer"*。Web 客户端也确实渲染了「输入你的答案」输入框。
**只有飞书这条通道不支** —— 桥的 `questionCard()` 只画按钮，无选项时退化成一个
「确认已读」按钮，点了回 `custom: '已确认'`，语义完全是错的。

目的：

1. 让飞书卡片能收集自由文本，且**不牺牲"点一下就答完"的顺手程度**。
2. 把这条通道的表达拉到和 Web 客户端同一水平：有上下文、有后果说明、有逃生口、有回执。
3. 修掉三处语义错误：无选项不再等价于"已确认"；跳过与取消不再混为一谈；
   点完之后卡片不再纹丝不动。

非目标：

- **不改宿主 schema**。`ask_user_question` 的参数定义在 `@deepseek-ai/dsh-tool-ask-user`，
  桥只是接收方。想强制"一次只问一个""每个选项必须带 description"，得动上游包（fork），
  不在本次范围。桥能做的是**渲染层降级**：缺 description 就不占位、选项过多换下拉。
- 不做超时倒计时。桥只实现了 waterfall 的 `ask()`，timed 模式需要的 `wait` 通道没接，
  那是下一件事。

## 2. 架构与数据流

```
模型 → ask_user_question 工具调用
     → ctx.userQuestions.ask()  (宿主阻塞等待)
     → 'user-questions/request' waterfall
     → 桥的 onQuestion 认领（bridge.ts，注册于 profile 无 web-app 时）
     → createQuestionProvider().provider.ask()
     → 发 CardKit 2.0 卡片（每问一个 form）
     → 用户点按钮 / 提交文字 → card.action.trigger
     → handleCardAction：解析 action.name → 记录该问答案 → updateCard 回执
     → 全部问题答完 → resolve { answers: [...] } → 工具结果回灌 agent loop
```

关键数据不是 `behaviors.value`，而是 **元素 `name`**：

```
q<token>f<i>      问题 i 的 form 容器
q<token>a<i>      问题 i 的输入框
q<token>o<i>_<j>  问题 i 的第 j 个选项按钮
q<token>t<i>      只提交文字
q<token>s<i>      跳过
```

`token` 是 8 位十六进制，一次 ask 一个。`name` 是 CardKit 里唯一保证全局唯一且
必定随 `action.name` 回传的标识（`behaviors.value` 在表单提交场景没有这条保证），
所以控件身份全部编码在这里，正则 `^q([0-9a-f]{8})([faots])(\d+)(?:_(\d+))?$` 解回来。

## 3. 契约设计

### 卡片形态

```
┌ 需要你的回答（header · 蓝 / 答完转绿）─────────┐
│ 问题正文（plain_text）                         │
│ 分组 · xxx（有 header 才出现）                  │
│ detail（有才出现）                             │
│ 选项A —— 后果说明                              │  ← 每个带 description 的选项一行
│ 选项B —— 后果说明                              │
│ ┌ form: q<token>f0 ─────────────────────────┐ │
│ │ [输入框 multiline rows=2 required=false]   │ │
│ │ [A] [B] [C]        （每行最多 3 个）        │ │
│ │                        [提交文字] [跳过]   │ │
│ └───────────────────────────────────────────┘ │
└───────────────────────────────────────────────┘
```

答完后该问题原地换成一行回执：

```
✅ 问题正文
你的选择 · 补充文本 · 21:06
```

### 为什么选项按钮就是提交按钮

`form_action_type: "submit"` 挂在每个选项按钮上，于是「选」和「交」是同一次点击。
用户填了文本再点选项，文本随 `formValue` 一起回传 —— 这就是
"选项为主、输入兜底"能成立而不用两步操作的原因。

**代价与必须守住的一条**：`input.required` 必须为 `false`。设成 `true`，点选项会被
前端以「有必填项未填写」拦下，回调根本发不出去，整张卡片变成死物。

### 答案映射

| 用户动作 | 回传标识 | 落成答案 |
|---|---|---|
| 点选项 | `o<i>_<j>` + `formValue` | `selected: [label]`，有文本则并入 `custom` |
| 只填文本 + 提交文字 | `t<i>` | `selected: []` + `custom: text` |
| 跳过 | `s<i>` | `selected: []`，**无 custom** |

跳过 ≠ 取消：宿主把 `selected: []` 且无 `custom` 读作"用户明确跳过了这一问"，
把取消（abort）读作 `custom: '[已取消]'`。两者混同会让模型把"你按判断来"
误解成"这事别提了"。

### 多问题

每问一个独立 `form`，并列在 `body.elements` 根级（CardKit 禁止 form 嵌套、
也禁止把它放进 `column_set`）。各自独立提交、独立回执，**全部答完才 resolve**。
先答第二个、再答第一个是合法的，第一个答完时 toast 报「已回答，还有 N 个问题」。

## 4. 失败路径

每条都是真实会发生的，不是防御性假设：

| 情形 | 处理 |
|---|---|
| 会话没有 chat 绑定 | 不发卡，返回 `custom: '[会话不可用]'`，模型不会挂死 |
| 卡片发送失败 | 返回 `custom: '[无法发送问题]'`，同上 |
| `updateCard` 失败 | 吞掉：答案已经记下，只是没回执。不因为装饰失败而丢答案 |
| 点了过期/伪造的 name | `handleCardAction` 返回 `undefined`，交给别的 handler 判定 |
| 文本为空却点「提交文字」 | toast 警告「还没有输入内容」，**不 settle**，问题仍可答 |
| 用户不答就走开 | abort 时以 `custom: '[已取消]'` 收尾 |
| 端口没有 `updateCard`（测试替身） | 可选方法，缺席则卡片保持可点，不回执 |

## 5. 测试三层

- **单元（`tests/questions.spec.ts`，11 条）**：卡片是 `schema: '2.0'`、每问一 form、
  `input.required === false`、控件 name 编码正确、选项/文本/跳过三种落成答案、
  空文本不 settle、多问未齐不 resolve、回执替换已答问题而其余 form 存活、
  陌生 name 不理、无绑定 fail closed、abort 取消。
- **契约形状（`tests/questions-toast.spec.ts`，2 条）**：toast 必须是对象
  `{ toast: { type, content } }`；`CardActionResponse` 是 `Record<string, unknown>`，
  SDK 原样转发不校验，裸字符串能过类型检查但平台会静默丢弃。
- **全量（`pnpm test`，77 个 spec / 831 条）**：含 `docs-consistency` 文档门。

真机尚未点过，见风险。

## 6. 风险与未验证项

- **CardKit 2.0 要求客户端 7.20+**。低于此版本卡片只剩标题和一行升级提示。
  桥原来发的是 1.0 结构（`config`/`elements`），对老客户端更宽容，这次是主动放弃。
- **`updateCard` 重建整卡，会重置兄弟表单里已输入但未提交的文本**。
  CardKit 只能整卡更新，做不到按元素刷新。取舍是"提交即回执"优先。
- **真机未验证**：表单提交后卡片能否被 `updateCard` 改写、多个 form 并列是否都被
  正常渲染、按钮 name 长度是否被接受 —— 逻辑与类型都过了，但都得在飞书里点一遍才算数。
- **单选语义**：选了选项又填文本时，回答是 `selected: [选项] + custom: 文本`。
  Web 客户端在单选场景是"文本替代选项"，两者不完全一致；桥这边不丢信息，更保守。
