# 设计卡：飞书功能原生化（agent 可调的飞书工具 + 桥原生能力合流）

> 状态：✅ M1 已交付 · 2026-09-09 立（维护方）· 需求方原话「要把飞书的各种功能在dsh上也用上既是插件也是我们桥的原生态」
> 前置：《设计卡_双端设置与同步》（P091）——工具随桥装入即生效，web/desktop 双形态同享

## 1. 背景

桥此前是单向的：把 agent 渲染给飞书（消息/卡片/审批），但 agent 本身不能「摸到」飞书——
它发不出主动消息、用不了飞书云盘。唯一例外是 `send_file`（2026-08 上线），证明
channel-owned tool 按聊天 agent 逐个注册的模式可行（`composeChatAgent` extraTools）。

飞书桥已有云客户端 `FeishuCloud`（0.5.0 为迁移/仲裁而建：tenant_token 缓存、根目录、
上传/列表/下载/删除），一直只是桥内部件，agent 够不着。

## 2. 目标（M1）

1. agent 能**主动发飞书消息**（长任务里程碑、定时任务完工、后台子代理需要关注时）。
2. agent 能把**飞书 app 自有云空间**当持久便签（跨设备/跨机存活，工作区删了也在）。
3. 全部走桥既有能力（replay 传输、FeishuCloud），不加新外部依赖；任何失败只进
   工具结果，不炸通道。

## 3. 设计（M1 交付，0.7.0）

`src/feishu-tools.ts`，工厂注入 `{port(replay), chatOfSession, credentials, fetchImpl}`，
随 `send_file` 一起传 `composeChatAgent`，逐 agent 注册 + 提示词段
（`dsh-lark-bridge:feishu-tools`, order 121，仅在工具在场时注入）：

| 工具 | 参数 | 行为 |
|---|---|---|
| `feishu_notify` | `text` 必填, `chat_id` 可省 | 经 replay 传输发 markdown；省 `chat_id` 时由 `exec.agent.session.id` 查会话→聊天绑定发进**当前聊天**；断线期间进 replay 队列 |
| `feishu_drive_write` | `name`, `content` | putJson 语义：传新→删旧同名，app 自有云空间 |
| `feishu_drive_read` | `name` | 最新同名文件原文；无则 `content: null` |
| `feishu_drive_list` | — | 根目录文件清单（name/token/modifiedMs） |

错误契约：无凭证/未绑定聊天/空参数 → `ok:false + error`，绝不 throw 出工具边界。

## 4. 验收（M1）

1. `feishu_notify` 默认发当前聊天、显式 `chat_id` 覆盖、未绑定+缺参干净拒绝（vitest）。
2. drive 三工具经假飞书 API（token→根目录→upload_all→列目录→下载→删除全链路）往返一致。
3. 无凭证时 drive 工具拒绝而不炸；`feishu_notify` 不受凭证影响（走传输不走 API）。
4. tsc 全绿；契约测试 43/43；泄漏检查 exit 0。
