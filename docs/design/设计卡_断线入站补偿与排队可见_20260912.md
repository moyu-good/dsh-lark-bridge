# 设计卡 · 断线入站补偿与排队可见（P140）

> 立案：2026-09-12（P140，运营方令"深度解决"）
> 关联：P023（dsh 桥持续开发）、P045（桥四大增强）

## 背景（证据）

运营方报告两症状，多次复现：①一个对话框连发第二条消息"直接卡死"；②做完一个任务后下一个任务不响应。

7 天运行时取证（journalctl dsh-lark-bridge）：
- 飞书长连接 **12 次断线**（其中 11 次在 09-12 当天，最长 12 分钟 10:51→11:03），每次断线窗口**入站事件永久丢失**（transport 无 replay/cursor，src/bridge.ts 注释自认）。
- 服务重启 5 次/7 天（09-12 两次：13:08、17:01），进程死了同样收不到消息。
- 排除项：云端仲裁 standby 退避 7 天 **0** 次；LLM 错误（429/LlmError/agent/error）7 天 **0** 次；readDeviceState 为本地文件读无挂起。
- followup 语义核查（packages/core/agent-loop/src/agent.ts）：入队 next-turn + 唤醒 driver，live driver 在 turn 边界认领队列——机制健全，**无死锁**。但排队对用户完全不可见：第二条消息只有一个 reaction 反馈，聊天面无任何输出 → 感知为"卡死"。

结论：症状主因 = 断线窗口静默丢消息 + 排队不可见，非并发死锁。

## 目的

1. 断线恢复后，让 chat 知道"刚才丢过消息"，把静默丢失变成可行动信号。
2. agent 忙时到达的消息给出排队回执，消除"卡死"感知。

## 设计

1. bridge.ts 增加断线 gap 追踪：`reconnecting` 记 `disconnectedAt`（不覆盖已有值）；`reconnected` 计算 gap，≥30s 时向所有已绑定 chat（bySession 去重）各发一条补偿提示，注明中断时长与"期间消息不补送，请重发"。fire-and-forget（void + catch），一次 gap 至多一轮。
2. handleMessage 在投喂 followup 前检查 `agent.status === 'running'`（host.ts 的 HostAgent 接口增可选 `status?: string`——真实 ReactLoopAgent 提供，测试替身可省略）；running 则向 chat 发一条短排队回执（每条消息一条，文案一行）。
3. 不动 harness 核心（agent-loop 0 错误证据，不支持大爆炸半径）；不 tune keepalive 参数（网络层抖动非参数可治）。

## 验收标准

- `pnpm build` 通过、`vitest run` 全绿。
- 服务重启后 journal 出现 ws ready 且无报错。
- 行为验收（运营方配合）：①正常单发有回复；②任务执行中连发第二条，收到"⏳ 已排队"回执且任务完成后被处理；③拔网/断线 ≥30s 恢复后，chat 收到补偿提示。

## 风险

- 断线补偿提示在无绑定 chat 时静默跳过（无收件人）——预期行为。
- 排队回执在群聊可能略刷屏——当前部署为私聊 bot，接受；后续可加节流。
- host.ts 接口加可选字段对既有实现向后兼容（可选）。
