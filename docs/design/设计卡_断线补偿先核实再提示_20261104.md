# 设计卡 · 断线补偿改为「先核实再提示」（P140 修订）

> 立案：2026-11-04（运营方质疑"这条提示有必要吗"）
> 关联：P140（断线入站补偿与排队可见，2026-09-12）

## 背景（证据）

P140 的补偿提示是"按 gap 发"：重连后只要中断 ≥30 秒，就给每个绑定群发一句
`⚠️ 连接中断了约 N 分钟——期间发来的消息飞书不会补送，重要指令请重发。`

2026-11-04 运营方直接质疑：**"你没回复我就知道断了，发这个有必要吗？"** 这个
质疑成立——提示说的是"可能有消息丢了"，而不是"确实丢了"；断线窗口里一条消息
都没有时，它仍然是噪音，而且以 agent 的口吻发出，看起来像在刷存在感。

但 P140 要解决的事实没变：长连接没有游标，断线窗口里的入站事件在到达桥之前
就没了；飞书客户端那边消息显示"发送成功"，用户无法区分"没送到"和"在忙/卡死"。

## 关键事实（本次核实）

- `tenant_access_token` 调 `GET /open-apis/im/v1/messages` 返回 `code: 0`：
  本应用已具备 `im:message:readonly`，能按 chat + 时间窗口把断线期间的消息读回来。
- 返回项带 `sender.sender_type`（`user` / `app`）与 `create_time`（ms），
  足以区分"人发的"和"本应用自己发的"，并只统计窗口内的人消息。

## 设计

1. `FeishuCloud.listMessages(chatId, startMs, endMs, maxPages=5)`：按秒级
   `start_time`/`end_time` 拉窗口内消息，翻页有上限（250 条），只取
   `messageId`/`senderType`/`createTimeMs`/`msgType`。
2. `bridge.ts` 的 `reconnected` 不再直接发提示，而是走 `reportGap`：
   - 对每个绑定 chat 拉一次窗口历史，统计 `sender_type === 'user'` 的条数；
   - 有 N 条 → 发「刚才连接断了约 X，这期间你有 N 条消息没送到，请重发」；
   - 0 条 → 静默（只写 debug 日志）；
   - 拉取失败（无凭证/无权限/网络）→ 退回原通用提示，保证不漏报。
3. 新增配置 `gapNoticeMinMs`（默认 30_000，`0` 关闭）。它现在只过滤亚秒级
   抖动：既然"没丢就不发"，阈值不需要靠"够长才值得说"来降噪。
4. `installBridge` 增加可选 `deps.fetchImpl` 接缝，`runtime.internals.fetchImpl`
   供测试注入；生产不传，走全局 fetch。

## 验收标准

- `pnpm typecheck` 通过；`pnpm build` 产出新 `lib/types-<hash>.js`。
- `tests/gap-notice.spec.ts` 五条全绿：有遗漏点名条数 / 无遗漏静默 /
  拉取失败兜底 / 短于阈值不打扰 / `gapNoticeMinMs = 0` 全关。
- `tests/docs-consistency.spec.ts` 通过（README 测试数、套件数同步）。
- 行为验收（运营方配合）：断线 ≥30 秒且期间发过消息 → 收到含具体条数的提示；
  断线但没发消息 → 无提示。

## 风险

- 每个绑定 chat 每次断线多一次 API 调用；断线本身不频繁，且飞书该接口配额充足。
- 窗口边界用本地 `Date.now()`，与服务器 `create_time` 可能差 1–2 秒；
  极端情况下把刚发的一条算进窗口，只会多说一句，不会漏报。
- 无 `im:message:readonly` 的部署自动退回通用提示，行为与 P140 原版一致。
- 断线期间消息仍不会自动补处理（只提示重发）：自动重放会带来重复执行副作用，
  长期看"告知 + 让人决定"比"悄悄重放"安全。
