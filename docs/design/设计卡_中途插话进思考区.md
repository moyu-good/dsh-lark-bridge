# 设计卡：中途插话进思考区（dsh-lark-bridge）

> 状态：现行设计 · 2026-10-30 建档 · CHENJIAMIAN

## 1. 目的与非目标

**目的**：让「跑到一半插话」的那句话出现在飞书原生思考区（CoT）里，位置精确到它让 Agent 改方向的那一步之前。

**起因**（2026-10-30 真实反馈）：`busyPolicy: steer` 下用户插话，聊天里只有一条回执「🎯 已插话：下一个 step 边界生效」，话本身不进任何可见位置。用户看到 Agent 确实转向了，却无从知道是什么让它转的；事后翻记录也查不到插话在第几步、说了什么。

**非目标**：

- 不改 `busyPolicy` 的三种投递语义（`queue` / `steer` / `inject`）。
- 不在思考区里显示宿主自己写进会话的消息（goal、指令、上下文、提醒）——那些不是读者自己的句子。
- 不动 `stream` 渲染器（老客户端退化路径只出打字机卡片，没有思考区可言）。

## 2. 架构与数据流

宿主对「轮中消息」的记录方式是本设计的事实基础，实测于 `~/.dsh/sessions/**/session.v4.jsonl.zstd`（按 zstd magic 切帧解压统计）：

- 消息**到达时**不落盘：它进 agent 收件箱。
- 在下一个 step 边界被**接纳**时，才以 `user/message` 追加进会话日志，`surfaceOp: "append"`。
- 因此它在时间线上夹在两步之间：`step/start(n) … user/message … step/start(n+1)`。
- 一次会话 54 个 turn、13 条 `source.kind === 'user'` 的 `user/message`，全部落在 `step >= 2`——**开轮那条消息不以这个事件出现**，这正好区分了「开轮」与「插话」。

载荷形状（实测）：

```json
{ "type": "user/message", "surfaceOp": "append",
  "data": { "id": "…", "role": "user",
            "content": [{ "type": "text", "text": "改成先看测试" }],
            "source": { "kind": "user" } } }
```

`source.kind` 的其他取值（`agent-instructions` / `runtime-context` / `goal` / `skill-catalog` / `tool-jobs` / `repeat-tool-reminder`）全是宿主自述，一律不显示。

数据流：

```
宿主 step 边界接纳 → session/event('user/message')
  → cot.ts isUserChatMessageEvent（只认 source.kind==='user'）
  → 有活跃 run 且未结束才处理（开轮那条 live 尚未建立，自然被挡掉）
  → 关掉当前 reasoning 块
  → TEXT_MESSAGE_START{role:'user'} / CONTENT / END 入队
  → 飞书渲染成读者自己的一段话
```

## 3. 契约设计

- `host.ts` 新增 `UserChatMessageData` 与 `isUserChatMessageEvent`。守卫同时接受两种载荷形状（消息在 `data` 本身，或在 `data.message` 下），因为团队中继用的是后者。
- `cot.ts` 的 `LiveRun` 增加 `userMessages` 计数，用于给每个插话分配独立 `messageId`（`user-<turn>-<n>`），避免两次插话在客户端合并成一段。
- 文本上限 1200 字符（`USER_MESSAGE_CHARS`）：CoT 单事件载荷上限 4096，粘贴长日志时截断而不是撑爆。
- 位置契约：插话事件必须排在它之前那次 `TOOL_CALL_END` 之后、下一个 `STEP` 之前——测试直接断言这个次序。

## 4. 失败路径

| 失败 | 处理 |
|---|---|
| `role: 'user'` 不被平台接受 | 与现有 `writeCotEvents` 同一条 `onFailure` 上报，答案不受影响（思考过程是展示层） |
| 消息在 `turn/end` 之后到达 | `live === undefined` 或 `finished` → 跳过；下一轮会以正常气泡出现 |
| 开轮消息被误显示 | `step/start` 之前没有活跃 run，天然挡住；测试锁定该行为 |
| 宿主改形状（`data.message` 包裹） | 守卫两种形状都认，不依赖单一实现 |
| 宿主某天开始为开轮消息也发该事件 | 只会多显示一条已在聊天里有气泡的消息；不影响正确性，但需复查本卡 |

## 5. 测试三层

- **mock 单测**：`tests/cot.spec.ts` 新增 `mid-turn messages (steering)` 三条——插话显示且位置正确、开轮消息不重复、宿主自述消息不显示。
- **plugin-contract**：未新增契约项（不改宿主接口，只消费既有 `user/message` 事件）。
- **smoke-live**：需真机验证一次 `steer` 插话在飞书客户端的渲染效果（`role:'user'` 的实际外观）。
