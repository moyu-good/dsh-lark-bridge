# 设计卡：桥双端设置与同步（bot 设置插件化 + web/desktop 全量同步）

> 状态：🚧 开发中 · 2026-08-31 立（zcode）· 需求方钦定今晚长线
> 依据：上游 dsh-desktop issue #93（web→desktop 插件不互通，已标记 Fixed in source 待发布）+ #1485（两 host 共写插件树会损坏会话名单）

## 1. 背景

- DSH Desktop 2.0.0 首启创建独立 `desktop` profile，与 `web` profile **插件树互不相通**：会话/主题/默认模型已经过 `~/.dsh` 共享，插件与桥配置没有——"对话还在，插件丢了"（社区 #93 原话）。
- 上游明确警告（#1485）：**两个 host 同时写同一插件树会损坏 workspace 会话名单** → 任何"共享目录式"同步都被禁止。
- 桥现状：bot 设置（appId/appSecret/locale/provider/model/cwd）由 profile 组装注入 Config，改一次要动部署；slash-panel 同步只管飞书面板，与 bot 配置无关。

## 2. 目标（需求方 08-31 钦定）

1. **bot 设置和同步操作插件化**：装了桥之后，网页端和 desktop（app版）**都能**方便地查看/修改 bot 设置、触发同步。
2. **所有内容双端同步**：设置、插件清单、会话内容在 web 形态与 desktop 形态之间一致。

## 3. 架构（三层）

### L1 设置单源（settings single source）
- `~/.dsh/dsh-lark-bridge/settings.json`：桥自管理配置单源。原子写（tmp+rename）+ 进程锁（O_EXCL lockfile + 陈锁接管）。
- 桥启动时：profile 注入 Config ⊕ settings.json 合并（settings.json 覆盖同名字段——它是"用户在 UI 里改过的那份"）。
- 变更热应用；影响传输层的字段（appId/appSecret/domain）变更时发 Feishu 确认卡，确认后重连通道。
- secret 字段任何 UI/日志只显示尾 4 位。posix 权限 600。

### L2 端发现（peers）
- `~/.dsh/dsh-lark-bridge/peers.json`：心跳条目 {profile, form: web|desktop, port, pid, bridgeVersion, ts}，30s TTL，原子写 last-writer-wins。
- 每端可呈现"另一端在线/离线"；所有同步动作以 peer 为单位发起。

### L3 同步引擎（内容三分类，三种策略）
| 内容 | 策略 |
|---|---|
| A. 桥设置 | settings.json 单源天然同步；冲突 last-writer-wins + 改前备份 settings.json.bak-<ts> |
| B. 插件清单（#93 正解） | `/bot sync-plugins`：经对端 control API（或扫对端 harness home）读对端 profile 插件清单 → diff → **预览卡确认** → 逐个 `dsh plugin add` 装进**本端** profile。绝不共写活体树（规避 #1485） |
| C. 会话内容 | 上游已经 ~/.dsh 共享——不造轮子，文档说明即可 |

- 控制通道：每端桥起 **127.0.0.1-only control API**（一次性 token，对齐上游 0.1.2 web 鉴权范式），供对端拉清单/触发动作；Feishu 卡片做人机确认层。

## 4. 交付切分（今晚长线，按序）

- **M1** settings.json 单源：src/sync/settings-store.ts（原子写/锁/合并/备份）
- **M2** peers.json 心跳与发现：src/sync/peers.ts
- **M3** control API + 一次性 token：src/sync/control-api.ts
- **M4** 插件清单同步 dry-run→确认→安装：src/sync/plugin-sync.ts
- **M5** Feishu `/bot 设置` 卡片 + 确认卡：src/settings-card.ts
- **M6** i18n（中英）+ invariant 守门 + vitest（fs mock）+ README/docs

## 5. 风险与边界

- #1485 活体树损坏：B 只做**清单导入**，永不共写插件树。
- desktop profile 由 Desktop 2.0.0 启动器管理：同步安装必须复用其 CLI 语义；desktop 进程持锁时提示"到桌面端确认"。
- 热应用边界：传输层字段变更 = 确认卡重连，不静默。
- `~/.dsh` 在双端不同机时退化为"单源失效"——M1 设计为 `DSH_HOME` 可指向同一同步盘目录（用户自选），不强行做网络同步。

## 6. 验收

1. web profile 改 provider/model → desktop 端桥读到新值（无需重启）。
2. desktop 装 X 插件 → web 端 `/bot sync-plugins` 预览 diff → 确认 → web profile 出现 X。
3. 全程无 #1485 类损坏：会话名单两端完整。
4. tsc/vitest/契约/smoke 四门禁全绿。

## 8. 部署实录（2026-08-31 web 端已上线）

- **关键坑**：包入口是 `lib/index.js`（tsdown 产物）——改 src 后必须 `npm run build` 再重启，否则跑的是旧代码（本次踩实：sync 层静默不启动）。
- **web 端（WSL systemd）**：drop-in `/etc/systemd/system/dsh-feishu-chat.service.d/sync.conf` 设
  `DSH_SYNC_HOME=/mnt/c/<win-user>/.dsh` + `DSH_PROFILE=web` + `DSH_FORM=web`。
  共享 home 选 Windows 侧（desktop 原生 home），web 经 /mnt/c 读写。
- **跨端连通实测**：Windows→WSL localhost 转发单向可用——desktop 可直打 web 的 control API（:38825 health/manifest 实测 200）；反向不可达 → **manifest 随心跳带内传输**（PeerEntry.manifest），插件同步不依赖 API 连通方向。
- **共享设置 overlay 已接入 bootstrap**：shared file 逐键覆盖 profile 注入与 host settings scope。
- **凭证决策**：appId/appSecret 可以通过 /bot set 进共享文件（两端都有意采用时），但**同一 Feishu app 双端同时连 = 事件双投递双回复**。默认建议：第二端用独立 Feishu 自建应用，或单端活跃另一端 standby。
- **desktop 端待办**：安装 DSH Desktop 2.0.0（anywhere-labs）→ `dsh plugin --profile desktop add <桥源>` → 其进程环境设 `DSH_FORM=desktop`、`DSH_SYNC_HOME` 指向用户目录的 `.dsh` → /bot 互见。
