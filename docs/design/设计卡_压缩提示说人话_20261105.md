# 设计卡 · 压缩提示说人话（P140 续）

> 立案：2026-11-05（运营方反馈两条消息看不懂）
> 关联：P140（断线入站补偿与排队可见）、设计卡_断线补偿先核实再提示_20261104

## 背景（原话）

运营方贴出两条桥接消息：

```
📦 上下文压缩完成，释放约 49212 tokens
##### Primary Request and Intent
- Chat bound to `D:\Desktop\kehua-plus-hub`; user writes Chinese...
- Goal `goal-8c680dae-...`
优化这个东西

🗑️ 已修剪 1 条旧消息（释放约 2301 tokens）
```

第一句的问题是：把模型写的压缩摘要原样贴进聊天。摘要常常是英文模板
（`Primary Request and Intent`），里面还有 goal id、目录路径和用户自己的原话，
在飞书里渲染成标题 + 列表，像一段调试输出。

第二句的问题是：只说了条数，没说修剪的是什么。用户看到「1 条旧消息」无从判断
丢的是不是重要内容。

## 设计

1. **不贴摘要正文**。摘要的价值是给模型续接上下文，不是给用户读的；聊天里只需要
   知道"历史被折叠了、折了多少"。`compactionSummaryLine` 不再接收 `summary`。
2. **按来源归类被折叠的记录**。`compaction/*` 事件只带 `shadowedSeqs`（会话日志
   序号），桥接用 `session.eventAt(seq)` 把每个序号读回来，按事件类型计数：
   `user/message` → 你的提问，`assistant/message` → 我的回复，
   `tool/call` → 工具调用，`tool/result` → 工具输出，其余 → 其它记录。
   读不到的序号记进"其它"，不猜。
3. **只列非零的类别**，顺序固定：提问、回复、工具调用、工具输出、其它。
   全为零或拿不到 breakdown 时退回裸条数，不留空括号。
4. 数字统一千分位（`49,212` 而不是 `49212`）。

最终文案：

```
📦 上下文压缩完成：3 条较早消息（1 条你的提问、1 条我的回复、1 条工具输出）已换成摘要，释放约 49,212 tokens
🗑️ 已修剪 5 条旧消息（5 条工具输出），释放约 4,321 tokens
```

## 验收标准

- `tests/notices.spec.ts`：压缩行不含摘要正文、带条数与分类；无 breakdown 时一行到底。
- `tests/compaction-notice.spec.ts`：`ctx.emit('session/event', …)` 走真实桥接，
  断言修剪/压缩提示里出现分类；超出日志末尾的序号记"其它"。
- `pnpm typecheck`、`pnpm build` 通过；docs 一致性检查通过。

## 风险

- 每次压缩/修剪多读 N 次 `eventAt`（纯内存查表），代价可忽略。
- 分类只到"类别"粒度，不贴具体内容：贴内容会再次把消息撑成调试输出，
  与本次优化目标相反。真要看原文，会话日志在 `~/.dsh/sessions/`。
- 事件类型名来自宿主契约（`user/message` 等）；宿主改名时分类会整体落到"其它"，
  提示退化成裸条数——可见但不崩，`tests/compaction-notice.spec.ts` 会在改名的
  宿主流上先红。
