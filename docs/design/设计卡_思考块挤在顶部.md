# 设计卡：思考块不再挤在思考区顶部

> 状态：现行设计 · 2026-10-30 建档 · CHENJIAMIAN

## 1. 目的与非目标

**目的**：一轮对话里反复出现「思考 → 调工具 → 再思考」时，每一段思考出现在它**实际发生的位置**（两次工具调用之间），而不是全部堆在思考区最上面。

**起因**（2026-10-30 真机反馈）：用户插话后，模型继续思考、继续调工具；飞书思考区里所有思考文字集中在顶部，看不出哪段思考是为了哪次调用。

**非目标**：

- 不改工具调用的图标/标题渲染。
- 不改答案消息（答案本来就在聊天里，不在思考区）。
- 不改 `busyPolicy` 的三种投递语义。

## 2. 根因

`cot.ts` 里整轮所有 reasoning 事件共用同一个 `messageId`：`reasoning-<turn>`。

AG-UI 的 `REASONING_MESSAGE_START` 语义是 **Creates a new ReasoningMessage**，客户端按 `messageId` 归属消息。同一个 id 再发 START / CONTENT，等价于「更新那一条已有消息」——于是第二段、第三段思考全被并进第一块，位置留在最上面。

工具调用用的是 `callId` 派生的唯一 id，所以它们显示在正确位置；只有思考被合并。

## 3. 契约设计

- `LiveRun` 增加 `reasoningId`（当前打开块的 id）与 `reasoningBlocks`（本轮的计数）。
- `openReasoning(run)`：计数 +1，id 取 `reasoning-<turn>-<n>`，发 `REASONING_MESSAGE_START{role:'reasoning'}`；后续 delta 都带这个 id。
- `closeReasoning(run)`：用当前 `reasoningId` 发 `REASONING_MESSAGE_END`，幂等。
- 三个结束点统一走 `closeReasoning`：工具调用之前、插话之前、轮结束（`closeRun`）。
- `block-end` 整块到达（非流式适配器）时也新开一个 id，保证它落在当前位置。

## 4. 失败路径

| 失败 | 处理 |
|---|---|
| 平台本来就按「思考统一置顶」布局，与 id 无关 | 本改动无效；下一步改用 `TEXT_MESSAGE{role:'assistant'}` 交错渲染，或在工具调用事件之间补文本块 |
| 客户端对同 id 多 START 做去重，导致丢块 | 每个 id 唯一，只会多块，不会丢 |
| 一次工具调用前后没有新思考 | 不新开块，不产生空思考块 |
| 写事件失败 | 沿用既有 `onFailure`：思考过程是展示层，答案不受影响 |

## 5. 测试三层

- **mock 单测**：`tests/cot.spec.ts` 新增一条——两段思考的 `messageId` 不同，且第二段的 START 排在 `TOOL_CALL_END` 之后，每段 delta 归属自己的 id。
- **plugin-contract**：未新增（不改宿主接口）。
- **smoke-live**：2026-10-30 真机确认——插话后继续多轮工具调用，思考块各自落在对应工具调用之间，不再堆在顶部。结论：飞书客户端确实按 `messageId` 归属 reasoning 消息，第 4 节第一行的「平台统一置顶」假设不成立，备用方案不需要。
